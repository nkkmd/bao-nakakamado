## 実装の接続点

`next-turn-engine.js` は通常の種まき・捕獲・勝敗判定を、`steal.js` はその結果に対するNYAKUAの奪取と別確保を扱う。将来のAIは両者を含む `search-transition.js` のアダプターを使う。

| 入口 | 用途 |
|---|---|
| `NakakamadoSteal.applyWithEvents(game, move)` | 画面の演出と確定棋譜。局面スナップショットを生成する |
| `NakakamadoSearchTransition.createForEngine(E)` | 現行エンジンに結び付いた探索用アダプターを作る |
| アダプターの `moveVariants(state)` | NYAKUA後の局面でNYUMBAのstop/useを区別する |
| アダプターの `applyMove(state, move)` | 盤面だけを受け取り `{state, events, summary}` を返す。スナップショットと累積棋譜は生成しない |
| アダプターの `stateKey(state)` | 規則ID・版と現行盤面の全フィールドを含む局面識別 |
| アダプターの `outcome(state)` | `ongoing`、`normal-terminal`、`safety-stop` を区別する |

探索用のeventsには石の投入数・捕獲数などのメタデータを残す。奪取数は `summary.stolen` にあり、演出用のstealイベントは探索では追加しない。これはイベント完全削除や盤面コピー方式の高速化まで行ったものではない。性能効果は後続工程で測定する。

## 段階と完了条件

### 第1段階：計画とルール遷移の整備

通常の着手と軽量遷移の最終盤面、投入数、捕獲回数、奪取数、合法variantを一致させる。入力非変更、南北交換、全棋譜再構築、総KETE保存、境界条件、既知の安全停止を検証する。

完了条件は、不一致0件、必要な規則の検証欠落0件、既存回帰の失敗0件。検証対象のseed・候補遷移数・ソースハッシュを保存し、実画面の回帰もCIで確認する。ローカルとGitHub Actionsの実画面確認が通過し、第1段階の検証は完了した。[検証記録](AI_SEARCH_TRANSITION_VERIFICATION_20261004.md)で根拠と実行対象を管理する。2026年10月5日にPR #17でmainへ統合した。

### 第2段階：探索機構の移植

反復深化、Alpha-Beta系探索、PVS、手の順序付け、置換表、評価キャッシュ、静止探索など、移植元の実際の公開経路を確認して適応する。実験専用の別アルゴリズムを一律に取り込まない。最初はニャクア対応の手作り評価関数を使い、比較基準となる「探索版」を固定する。

すべての探索・順序付け・評価特徴の先読みがNYAKUA込みの遷移を通ることを確認する。移植元の `stateKey` は差し替え、`nyakuaReserve`、`pending`、終了理由を落とさない。現在のアダプターは手数も含めて保守的に区別しており、将来省く場合は別途妥当性を検証する。

浅い全探索との照合、強制勝敗の既知局面、合法手返却、時間切れ時の最後の完了探索の採用、入力非変更を必須とする。安全上限による停止を通常勝敗の確定値へ変換しない。循環を避ける探索上の扱いを決めても、それを新しいゲーム規則として適用しない。

### 第3段階：評価器の適応・学習

[専用設計](AI_LEARNING_DESIGN_20261004.md)と機械可読仕様に入力・教師・分割・再開を固定し、96生成単位・241局面の処理パイロットを実施した。JavaScript/Pythonの368bit入力482観点、部分・全完了の再開が一致。続く[実時計の教師試走](AI_TEACHER_FEASIBILITY_20261004.md)では、確保分のみの到達棋譜4件を含む64局面が深度4まで完了した。このパイロットと教師試走では学習は未実施。パイロットと教師試走は閲覧済みの開発用データで、正式な最終検証には使わない。

既存モデルは `nyakuaReserve` を入力として扱わず、通常ハンドへ単純加算しても「保護される・次の手番で必ず使う」という意味を表せない。既存モデル流用は検証候補とし、正式採用の根拠を元ゲームから引き継がない。

探索版で教師局面と教師評価を生成し、確保分、通常ハンド、NAMUA/MTAJI、NYUMBAなどを区別できる入力を定義する。3個投入・最後の1個・NAMUA終了付近の局面も確保する。教師の探索深度・完了状態を記録し、未完了探索や安全停止を確定勝敗のラベルにしない。

開幕・対局系列・対称変換をまたぐデータ漏洩を避けて、開発用・独立検証用・最終確認用を分ける。同じデータからの手作り評価、既存モデル流用、新規学習モデルを比較する。教師誤差、既知戦術、入力範囲、推論時間、探索全体の応答時間を確認する。

### 第4段階：棋力と端末の検証

同じBao Nakakamadoのルール・開始局面・持ち時間で、簡易版対探索版、探索版対学習評価器版を比較する。開始局面ごとに先後を交換し、ペアを統計の単位とする。通常終局、反復、手数上限、安全停止、技術的失敗を分けて報告する。元ゲームのAIとの異なるルール下の勝率を、そのまま棋力差としない。

正式対局の前に、対象集団、時間予算、局数、主要指標、採用・保留条件、独立確認用seedを固定する。数値基準は探索版の性能を測って実行可能性を確認してから定め、最終比較の結果を見て変更しない。勝率だけでなく、同時間の強度、到達深度、遅延の分布、技術的失敗も確認する。

Web Worker接続では要求ID・局面識別・新規対局時の取消し・古い応答の破棄・返却手の再検証を行う。失敗時の代替はBao Nakakamadoの合法手から選び、元ゲームのエンジンへ戻さない。難易度はeasy/normal/hard/expert相当を候補とし、移植元の時間予算を参考に実測で決める。

デスクトップ・スマホ幅のブラウザー回帰に加え、ユーザーのmoto g52j 5Gで連続対局・思考時間・操作応答を確認する。ブラウザー幅の検査を実機検査と読み替えない。

### 第5段階：採用・公開

結果をレビューし、条件を満たす構成だけを採用する。探索版のみの採用も選択肢とし、学習評価器の不合格で無理に採用しない。Bao Nakakamado専用のAI系統・モデル・採用識別情報を設け、移植元のrelease IDを完成版の識別子として流用しない。

README、設計、診断・棋譜メタデータ、画面、出典・MIT表示、同梱ファイルを同期し、既存棋譜の互換性を検査する。文書の最終監査、PR、main統合、配信用ZIP、公開サイト確認を行い、実際の公開日・URLを[変更履歴](ORIGIN_AND_HISTORY.md)へ記録する。

## 長時間処理と再開

教師データ生成、学習、長時間対局はGitHub Actionsを第一候補とする。seed単位・対局ペア単位で分割し、固定設定、ソース・モデルハッシュ、完了単位、途中結果を保存する。再開時は完了単位を再消費せず、未完了ペアを明示する。workflow run、attempt、artifact、実行環境を記録する。

学習環境の都合でローカルが適切なら、資源・所要時間・再開方法を明記して選ぶ。今回の遷移照合は短時間で完了するためローカルで実施し、同じ照合をCIへ組み込んだ。
